# 多通道麦克风、Mean4 与固定波束形成扫盲

日期：2026-07-15  
用途：帮助项目成员理解老师提供的 MATLAB 代码、四麦八通道设备，以及我们正在实现的实时语音增强链路。

## 1. 先用一句话说清楚任务

机器人上的外置设备有 **4 个物理麦克风**，USB 声卡却以 **8 通道 PCM** 形式输出。老师要求我们从有效的前 4 路中保留空间信息，使用他提供的固定波束形成滤波器，把目标方向附近的声音增强为一路单声道，再送进现有唤醒词、ASR、LLM、TTS 和动作 pipeline。

这不是简单地“把声音调大”，而是利用四个麦克风收到同一声音时存在的微小时间差和相位差，让目标方向的声音相加、其他方向和部分噪声相互抵消。

## 2. 四个麦克风为什么会录出八个通道

### 2.1 物理麦克风和数字通道不是同一个概念

- **物理麦克风**：设备上真正负责拾音的传感器，本设备有 4 个。
- **录音通道**：USB 音频设备交给操作系统的数据列数，本设备声明为 8 通道。
- **有效通道**：真正包含麦克风语音的通道。老师确认通常是前 4 路，即通道索引 `0,1,2,3`。

后 4 路可能是保留通道、弱噪声、零数据或设备内部未使用的槽位。它们存在不代表设备有八个物理麦克风。

### 2.2 八通道 PCM 如何排列

PCM 数据通常按时间点交错保存：

```text
时刻 0: ch0 ch1 ch2 ch3 ch4 ch5 ch6 ch7
时刻 1: ch0 ch1 ch2 ch3 ch4 ch5 ch6 ch7
时刻 2: ch0 ch1 ch2 ch3 ch4 ch5 ch6 ch7
...
```

因此，不能把连续的一大段字节直接当作某一个麦克风。必须先按照通道数 reshape，再选择有效通道。

### 2.3 为什么真机仍要核对一次

“前四路有效”已经得到老师确认和一次真机录音支持，但以下信息仍需实测：

1. 前四路是否每次启动都保持有效。
2. `ch0~ch3` 分别对应阵列上的哪个物理位置。
3. 设备重新枚举为 `hw:0,0` 或 `hw:2,0` 时，通道顺序是否改变。

设备号变化只表示 ALSA 声卡编号变化，不必然表示通道顺序变化；两者需要分开验证。

## 3. PCM16、采样率和帧长是什么意思

当前链路使用：

- 采样率：`16000 Hz`，即每秒每通道 16000 个采样点。
- 格式：`PCM16`，每个采样点 16 bit，也就是 2 bytes。
- 输入通道：设备原始 8 路，算法使用其中 4 路。
- 输出通道：单声道 1 路。

在 16 kHz 下：

| 时长 | 每通道采样点 | 单声道 PCM16 字节数 |
|---|---:|---:|
| 16 ms | 256 | 512 bytes |
| 20 ms | 320 | 640 bytes |
| 32 ms | 512 | 1024 bytes |

老师说的“输入一帧 16 ms，缓冲区有 16 ms，处理单元 32 ms，输出 16 ms”，意思是：算法每次收到新的 16 ms 数据，把它和上一段 16 ms 拼成 32 ms 分析窗口；处理后只向前输出新的 16 ms，从而实现连续流式处理，而不是每 32 ms 才跳跃一次。

## 4. Mean4 是什么

`mean4` 表示只取四个有效麦克风，然后逐采样点求平均：

```text
y[n] = (x0[n] + x1[n] + x2[n] + x3[n]) / 4
```

它的特点：

- 实现简单、稳定、计算量很小。
- 四路都有相似语音时，随机噪声可能被平均掉一部分。
- 不需要知道麦克风几何位置或目标方向。
- 不会真正“指向”某个角度。
- 如果各麦克风之间存在传播延迟，直接平均可能造成高频抵消或声音发闷。

它适合作为 **稳定基线和回退模式**。我们以后判断 beamformer 是否真的有提升，必须与 mean4 比较，而不是只听 beamformer 自己。

### 4.1 为什么不能平均全部八路

旧推流脚本在检测到多通道时会平均全部通道。如果后四路是零、弱噪声或无效信号，那么：

- 有效语音会被额外除以 8，音量下降。
- 无效通道噪声会被混入。
- 四麦空间信息完全丢失。

所以本设备的正确基线应是 **前四路 mean4**，不是八路平均。

## 5. Beamformer 是什么

`beamformer` 中文通常叫 **波束形成器**。它把多路麦克风看作一个阵列，根据目标方向对每路信号施加不同的延迟、相位和频率权重，再相加为一路输出。

直观理解：

1. 目标方向的声音到达四个麦克风的时间略有不同。
2. 波束形成器把这些差异补齐，使目标语音对齐后相加。
3. 其他方向的声音无法同时对齐，叠加时会部分抵消。

理想效果是目标方向语音更突出、旁侧声音和部分噪声更弱。它不是绝对消除噪声，也不保证任何环境都优于 mean4。

## 6. “固定波束形成”中的固定是什么意思

当前老师给的是 **固定波束形成器**：滤波权重提前算好，运行时不再根据声音方向动态调整。

例如这组权重针对大约 90 度方向，那么它一直“听”这个方向。优点是计算稳定、延迟小、便于流式部署；缺点是目标说话人换到其他方向时，增强效果可能下降。

后续若要支持 0、30、60、90、120、150、180 度，通常需要：

- 每个方向一组固定权重；或
- 先估计声源方向，再选择相应权重；或
- 使用自适应波束形成算法。

这次任务先完成老师提供方向的固定滤波器，不擅自扩成动态声源定位。

## 7. 老师提供的文件分别是什么

### `Fixed_Mini_Beamformer.m`

MATLAB 波束形成核心。它完成分帧、加窗、频域变换、四路复数权重处理、频域合成和时域重构。

### `test.m`

MATLAB 测试入口。它读取示例多通道录音，加载滤波器，调用波束形成器并写出结果。

### `DCF_Targ7.mat`

固定波束形成滤波器参数。转换后主要表现为一个四通道频域复数权重矩阵；当前参考权重形状为 `4 x 257`，对应四个有效输入通道和 512 点实数 FFT 的 257 个非负频点。

### `mixture.wav`

老师的多通道参考输入，用来验证算法转换是否正确。

### `out0.wav`

老师用 MATLAB 得到的参考输出。Python 版本应尽量与它逐采样一致，它是离线等价验证的“标准答案”。

## 8. 我们已经怎样把 MATLAB 转成 Python

当前仓库中的核心模块位于 `beamforming/`：

- `filter_io.py`：读取和转换滤波器权重。
- `fixed_mini_beamformer.py`：Python 固定波束形成算法。
- `stream_adapter.py`：把任意大小的多通道 PCM 输入整理成 16 ms 流式处理，并重新打包。
- `channel_diagnostics.py`：统计每路能量，判断哪些通道有效。
- `reference_verification.py`：与老师参考输出进行逐采样比较。

已有离线验证结果：Python 输出与老师的 `out0.wav` 基本完全一致，仅 6 个采样点相差 1 LSB。这说明 MATLAB 到 Python 的算法迁移是可信的。

已有流式验证结果：

- 每次输入 16 ms。
- 内部使用 32 ms 处理窗口。
- 每次推进并输出 16 ms。
- 最终再放入 FIFO，按照现有 UDP 协议每 20 ms 发送 640 bytes 单声道 PCM16。

## 9. 为什么算法是 16 ms，UDP 却是 20 ms

这是两个不同层级的约束：

- **beamformer 内部步长**：老师指定 16 ms。
- **现有机器人到 WSL 语音链协议**：每包 20 ms、640 bytes。

因此中间需要一个单声道 FIFO：

```text
8ch PCM16
  -> 选择前四路
  -> 每 16 ms 推进 beamformer
  -> 得到连续单声道 PCM
  -> 放入 FIFO
  -> FIFO 每满 320 个采样点就发一个 20 ms UDP 包
```

只要 FIFO 连续、不丢样、不重复，16 ms 和 20 ms 可以安全共存，不会凭空增加一个完整处理窗口的延迟。

## 10. 老师真正要求我们完成什么

根据老师的文字和文件，本阶段交付目标是：

1. 保留外置阵列的原始多通道输入，不在采集端提前混成单声道。
2. 从 8 路中确认并选择 4 路有效麦克风。
3. 将 MATLAB 固定波束形成算法和 `.mat` 滤波器转为 Python。
4. 按 16 ms 输入、32 ms 处理、16 ms 输出实现流式处理。
5. 输出一路增强后的单声道语音。
6. 接入现有唤醒词和 ASR pipeline。
7. 用不同角度录音和真机对话比较增强效果与延迟。

老师问“beamforming 那里实现得怎样”，核心不是问有没有普通降噪，而是问：**四麦阵列的固定方向增强是否已经按实时 Python pipeline 的形式实现并验证。**

## 11. 当前三种信号路径的区别

### 单路麦克风

只取某一路。优点是最原始；缺点是可能刚好选到较弱或受遮挡的麦克风。

### Mean4

前四路平均。它是稳定、安全的基线，但没有方向选择能力。

### Fixed Beamformer

前四路经过老师提供的方向滤波器。它有方向性，但高度依赖通道顺序、滤波器目标角度和真实阵列安装方向。

所以合理的验证不是问“哪个听起来最大声”，而是同时比较：

- 目标方向语音清晰度。
- 非目标方向抑制。
- 唤醒成功率。
- ASR 正确率。
- 端到端延迟。
- 是否削波、音爆、丢包或断续。

## 12. 为什么第一次真机听感可能是 Mean4 更清晰

这并不必然说明 Python 算法错误。常见原因包括：

1. 当前人声方向不等于滤波器设计方向。
2. 前四个数字通道与滤波器假定的物理麦克风顺序不一致。
3. 阵列安装朝向与老师生成滤波器时的角度坐标不同。
4. 机器人自身噪声来自滤波器主瓣方向。
5. 输出增益不同，导致主观比较不公平。
6. 固定波束在当前混响环境下不占优势。

因此 mean4 更清晰是很重要的诊断结果，但不能仅凭一次听感判定 beamformer 不可用。

## 13. 接下来怎样做，才不会破坏已跑通的 pipeline

### 离线阶段（机器人充电时完成）

1. 推流入口增加 `mean4` 和 `beamformer` 两种模式。
2. 默认保持 `mean4`，保证稳定回退。
3. 用已保存的真实 8 通道 WAV 模拟实时输入。
4. 验证 16 ms 分帧、32 ms 处理、20 ms UDP 打包无丢样和重复。
5. 为通道选择、均值和波束模式补自动测试。

### 真机阶段

1. 自动识别 `hw:0,0` / `hw:2,0`，但强制成功打开 8 通道。
2. 保存一段原始 8 通道录音并重新确认有效通道。
3. 校准前四路与物理麦克风位置的对应关系。
4. A/B 测试 `mean4` 与 `beamformer`。
5. 再把默认模式从 `mean4` 切到经过验证的 beamformer。

## 14. 安全原则和回退方式

- 不在 WSL 里直接创建 Unitree `AudioClient`，避免再次触发机器人模式切换和音爆问题。
- TTS、灯光、动作继续走 Jetson relay。
- 麦克风处理失败时不静默吞掉错误，应明确显示通道数、设备号和模式。
- `mean4` 始终保留为回退模式。
- beamformer 未完成真机 A/B 验证前，不设为默认。
- 原始 8 通道录音要保留，便于离线复现，不能只保存处理后的单声道。

## 15. 一句话记忆

**4 个物理麦克风通过 8 通道 USB 接口输出，前 4 路是有效阵列信号；mean4 是稳定平均基线，fixed beamformer 是利用四路空间差异增强固定方向；我们的任务是把老师的 MATLAB 滤波器做成 16 ms 流式 Python 处理，并在不破坏现有 20 ms UDP/ASR pipeline 的前提下完成真机验证。**
